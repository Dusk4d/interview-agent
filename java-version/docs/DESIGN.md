# 设计说明

本文记录实现中的关键取舍，以及「为什么不那样做」。面试时被追问设计动机时，这里的内容可以直接对应到代码。

## 1. 总体流程与职责边界

```text
导入简历
  └─ 校验(扩展名/大小/可读性) → 提取文本(PDF/DOCX/TXT) → 清洗 → 事实结构化 → 脱敏 → 落库 + 写向量库
练习/面试
  └─ 创建会话(状态机 CREATED/RESUME_READY/INTERVIEW_STARTED)
     └─ 选题方向(覆盖度 + 阶段) → 检索(RAG) → 出题(结构化 JSON) → WAITING_ANSWER
        └─ 提交回答 → 评估(四维 Rubric) → FOLLOW_UP / NEXT_QUESTION
           └─ ... → FINISHED → 报告(统计 + 模型定性 + Markdown)
```

**边界**：模型负责语言任务（出题、评估、写总结），程序负责状态、次数、校验与最终结果。
模型输出永远是「建议」，要经过解析与校验才可能改变状态。

## 2. 为什么是「有限状态机 + 有限工具」

| 备选 | 问题 |
|---|---|
| 一个大 Prompt 里让模型决定下一步 | 无法测试、不可恢复、价格与延迟不可控，出问题时无法定位是检索错还是模型乱说 |
| 固定顺序调用多个 Prompt | 不能根据回答质量追问/换题，退化成「题库播放器」 |
| **采用：显式状态机 + 条件路由** | 状态可枚举、可断言；路由条件在代码里，可解释、可回归测试 |

状态定义与转移表：`agent/InterviewStateMachine.java`（含 7 项测试覆盖终态封闭与非法转移）。

### 追问决策规则

```
评估.followUpRecommended == true
  且 当前问题不是追问本身
  且 本题追问次数 < app.interview.follow-up-limit-per-question（默认 1）
  且 题目配额未用尽
  → 状态置为 FOLLOW_UP（前端可「继续追问」或直接「下一题」）
否则 → NEXT_QUESTION
```

## 3. 为什么同时用向量召回和关键词召回

离线环境下默认使用进程内哈希向量（`LocalHashEmbeddingClient`）。它的问题很明确：**同义改写召回弱**。
因此 `DocumentRetriever` 并行跑两路：

1. 向量召回（余弦相似度，元数据过滤）
2. 关键词召回（token 覆盖率 + 项目名/主题名命中，中文补 2-gram）
3. RRF 融合（`DENSE 0.65 / LEXICAL 0.35`，`k=60`）

实测效果：查询「Redis 分布式锁」能稳定命中简历中的项目片段；换成纯关键词或纯向量都会漏。
`app.embedding.mode=remote` 时切换为 nomic-embed-text，远端不可用自动降级并记录 `degraded`。

## 4. 为什么「检索为空不硬凑」

方案书明确要求：检索为空不能被当作有依据。实现上：

* `minScore` 以下直接过滤，命中为空返回 `empty=true`；
* 出题上下文为空时，`InterviewService` 回退到**简历事实原文**（仍然是真实存在的内容），
  并由模板出题要求模型围绕该事实提问；
* 前端展示 `citations`，用户可点开 `/api/retrieval/search` 复核。

## 5. 评分的可解释性与稳定性

* 维度固定四项、等权 0.25，总分加权后保留两位小数（`AnswerEvaluator`）。
* 每个维度必须有 `reason`，缺字段视为结构化失败 → 降级，而不是把缺失当 0 分。
* 提示词中写死：不得替候选人补写指标；团队成果不得自动算作个人成果。
* `evidenceWarnings` 单独收集「没有证据的强主张」（例如说「提升了性能」但没有数字）。
* 降级评分（`HeuristicEvaluator`）分数上限 3.5、四维依据全部来自可观测特征（长度/机制词/结果词/结构词），
  并在结果中标记 `degraded=true`，前端与报告都会说明「本次为降级评估」。

**已知不足**：评分主观性未被量化。方案书要求的「同一回答重复运行比较分数差异」尚未执行，属于待测项（见 `VERIFICATION.md`）。

## 6. 结构化输出的四步修复

`StructuredOutputParser` 按由宽到严的顺序尝试：

1. 剥离 markdown 代码围栏；
2. 从解释性文本中截取第一个平衡的 `{...}`；
3. 修复常见瑕疵（中文引号、单引号、未加引号键、尾随逗号、注释）；
4. 截断修复（补全未闭合字符串/数组/对象）。

四步都失败 → 抛 `LLM_INVALID_STRUCTURE`，由上层降级并保留原始输出片段供排查。
`StructuredOutputParserTest` 用 11 个用例锁定了这些行为。

## 7. 隐私设计

| 数据 | 处理 |
|---|---|
| 手机号 / 邮箱 / 身份证 / 链接 / 地址 | 解析后立即替换为占位符（`PrivacyMasker`） |
| 简历原文（落库） | 存脱敏后的文本；原始文件不落盘 |
| 模型请求 | 只发送检索到的相关片段（不含联系方式），不发送整份简历 |
| 日志 | 只记录 id、数量、耗时、置信度；不记录简历原文 |
| 姓名 | 默认不脱敏（会误伤项目描述中的姓名）；可用 `app.privacy.mask-name=true` 开启 |

`PrivacyMasker#scan` 可用于自检；`PrivacyMaskerTest` 断言「技术数字（P99 800ms→210ms、QPS 3000）不被误伤」。

## 8. 文档解析的取舍

| 格式 | 方案 | 原因 |
|---|---|---|
| TXT/MD | 严格 UTF-8 解码，失败回退 GB18030 | 中文简历常见 GBK，乱码会污染事实抽取 |
| DOCX | 当 zip 读取 `word/document.xml`，单次扫描按 `<w:p>/<w:tr>/<w:tc>/<w:br>` 插入语义分隔 | 避免引入 POI + XMLBeans；表格按行保留「时间-公司-职责」关系 |
| PDF | PDFBox 3，逐页提取并保留换页语义 | 页眉页脚可按「重复行」被清洗阶段识别剔除 |
| 旧版 .doc | 明确拒绝并提示另存为 docx | 二进制格式解析风险高，不如给出清晰指引 |
| 图片型 PDF | 标记 `imageOnly` 并返回 422 明确提示 | 不做 OCR；绝不产出看似合理但无依据的结构 |

页眉页脚识别不靠关键词硬编码，而是「归一化后（数字替换为 #）在多页重复出现」，阈值可配。

## 9. 存储选择

* 默认 `file`（`<app.home>/data/*.json`）：原子写（临时文件 + move），单用户演示零安装成本，数据可读可备份。
* `memory`：测试与一次性演示。
* 抽象为 `InterviewRepository`，接 PostgreSQL + pgvector 时只需新增实现，服务层不改。

数据文件损坏时不会导致启动失败：改名隔离为 `*.corrupt` 后从空集合继续。

## 10. 上下文膨胀控制

`InterviewSession` 保存的是「必要上下文」而不是整场原文：

* `coveredTopics`：已覆盖项目/知识点，用于去重；
* `recentFeedback`：只保留最近 8 条评分摘要；
* `askedQuestionDigests`：问题摘要（60 字）用于避免重复提问；
* 报告生成时才拼接完整逐题记录，且每条回答截断到 200 字。

因此单次模型请求的上下文是**有界**的，不随轮次线性增长。

## 11. 参考回答（示范表达）的边界

方案书场景一要求返回「参考回答」，6.5 又同时要求「参考回答结构」。两者关系：

* `referenceAnswerStructure` 是**骨架**（背景 → 职责 → 机制 → 取舍 → 结果），永远返回；
* `referenceAnswer` 是按这个骨架组织、可照着复述的**示范表达**，可能为空。

它不是标准答案——项目面没有唯一正确答案。因此写进代码的约束是：

1. 只能用「用户自己说过的事实」+「简历事实片段」。缺少量化结果时输出占位符
   `（此处填入你的真实数据）`，不得替候选人编一个数字；
2. **代码层再挡一道**：`AnswerEvaluator` 会扫描示范表达里的量化指标
   （`3 倍`、`60%`、`200ms`、`1 万` 这类带量词/百分号的数字），只要在用户回答与给定事实里
   找不到出处，就**整段丢弃**并追加一条纠正说明。宁可没有参考回答，也不能给出一段用户会直接背去面试的编造内容。
   纯数字不参与校验，避免「第一步」「两个模块」被误杀；
3. 降级评估（模型不可用）时留空：启发式规则没有语义理解能力，硬拼一段「示范表达」只会看起来像真的。

实测（qwen3:1.7b）：回答里已有数字时参考回答完整保留；回答里没数字但简历里有，则复用简历数据；
两者都没有时模型没有编造，参考回答仍然干净。

## 12. 重答与换题的统计口径

「重新回答」与「换一道题」（方案书场景一）都会改动历史记录，这里的原则是**报告口径必须唯一**：

* `retry` 真删除旧回答与旧评分，而不是保留两份：否则同一道题会被平均分与能力雷达算两次；
  `recentFeedback` 里该题的旧摘要也一并替换，避免「第 1 题」在界面上出现两条不同分数；
* `replace` 删除被换掉的题并把 `questionCount` 还回去（换题不消耗配额），但**保留**它的
  `askedQuestionDigests` 指纹，否则模型会重新出一道一样的题；
* 换题次数没有新增持久化字段，而是用不变量推导：`askedQuestionDigests.size() - questionCount`
  就是换题次数（每出题都加指纹与题量，只有换题会减题量不减指纹）。该不变量由
  `RetryAndReplaceTest` 断言，改动出题流程时会被测出来；上限由
  `app.interview.max-question-skips` 控制（默认 3）。

## 13. 与方案书的差异（如实说明）

| 方案书建议 | 实际实现 | 原因 |
|---|---|---|
| Spring AI 编排 | 直接实现 OpenAI 兼容协议（JDK HttpClient） | 离线仓库无 Spring AI 完整依赖；协议收敛在一个类里，反而更容易替换供应商 |
| PostgreSQL + pgvector | 内存向量库（余弦 + 元数据过滤） | 本机无 PostgreSQL 服务；数据规模（几十~几百条）暴力检索足够，接口已抽象 |
| Redis 缓存 | 未使用 | 单用户本地演示无收益；会话状态本身很小 |
| Apache Tika/POI | 自实现 DOCX 提取 + PDFBox | 见第 8 节 |
| Vue3 + Element Plus 前端 | 零依赖原生 JS SPA | 离线无法安装 npm 依赖；本项目的重点在后端流程与反馈质量 |
| 数据模型 8 张表 | JSON 仓储 + record 领域模型 | 保留表结构等价物，必要时可直接映射为 SQL 表（字段一一对应） |
| 「重新回答」需保留历史以便对比 | 旧答案与旧评分直接删除 | 保留两份会污染报告统计口径（同一题算两次）；当前需求是「重来一次」，不是「版本对比」。若将来要做进步曲线，应改为带 `attempt` 序号的多版本存储 |
