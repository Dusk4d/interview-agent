# AI 面试陪练系统项目面经（规划稿）

> 当前项目尚未完成，本文用于指导开发和后续汇报。下面的回答是设计目标或待验证方案，不能直接当作已经完成的项目经历。完成后应根据真实代码、测试和个人贡献重新修改。

## 项目简介

这是一个简历驱动的 AI 面试陪练系统。用户导入本地简历后，系统提取项目、技术栈和经历信息，分别从项目面和计算机基础知识面生成问题；用户通过文字回答后，系统给出评分、问题分析和改正建议，并支持从开始、提问、回答、追问到总结的完整文本面试模拟。

当前已确认的是功能闭环；具体技术栈、模型调用方式、文件解析组件、评分维度、会话持久化和测试数据仍需按实际代码补充。不要在面试中把待确认内容说成已经完成。

## 简历 bullet 候选表述

- **事实结构化：**针对原始简历内容分散、直接提问容易脱离个人经历的问题，导入本地简历并按项目、技术栈和经历组织可检索内容，为后续项目面出题和回答反馈提供个人事实依据；支持的文件格式和解析组件待补充。
- **面试编排：**针对项目面、基础知识面和整体模拟面试目标不同的问题，按面试类型组织问题生成和多轮交互流程，使系统能够从单题回答延伸到追问、换题和阶段总结；具体路由条件和状态实现待补充。
- **答案评估：**针对用户只能得到题目、缺少针对性反馈的问题，对文字回答进行评分并指出遗漏和修正方向，将回答结果转化为可复习的反馈内容；评分维度、等级和结构化字段待补充。
- **闭环复盘：**针对单轮问答难以形成持续学习记录的问题，串联面试开始、问题生成、回答提交、评分纠错和整体总结，支持用户完成一次文本式模拟面试；历史会话和报告是否持久化待补充。

## 一句话口播

我做的是一个简历驱动的 AI 面试陪练系统，用户导入本地简历后，系统会结合简历中的项目经历和计算机基础知识生成问题，用户用文字回答后，系统再从回答质量、知识完整性和项目匹配度等角度给出评分与改进建议，同时支持从单题练习到完整文本面试模拟的闭环流程。这里的具体评分维度需要以我的实际实现为准。

## 面试问题与第一人称回答

### 1. 为什么要做这个项目？

**回答：**我做这个项目是因为通用的题库只能覆盖知识点，不能结合个人简历进行追问；而只让大模型生成几个问题，又很难形成持续的训练过程。所以我把简历导入、项目和八股出题、文字回答、评分纠错以及整体面试串成一个闭环。用户不是只看到一个答案，而是能够知道自己具体漏了什么、下一步应该补充什么，并且可以继续进行追问或进入下一道题。这个项目的目标是把一次性的问答变成可重复的面试训练流程。

**追问：这个项目解决的核心问题是什么？**

**回答：**核心问题是“个人经历和知识训练没有被放在同一个流程里”。传统题库能够问八股，但不一定知道候选人做过什么项目；普通聊天机器人能回答问题，但不一定按照面试流程追问和复盘。我的设计把简历当作用户自己的事实来源，再根据项目面或基础知识面选择问题类型，最后通过评分和纠错把回答转化成下一次可复习的内容。这样项目训练和基础知识训练可以在同一场会话里切换。

### 2. 系统整体架构和数据流是什么？

**回答：**整体流程可以分成文件导入、内容解析、知识组织、问题生成、回答评估和会话总结几个阶段。用户先导入本地简历，系统把原始文本整理成项目、技术栈、经历和知识主题等内容；开始面试后，根据当前模式检索相关内容并生成问题；用户提交文字回答后，评估模块分析答案，再把评分和改进建议展示出来。如果当前模式支持追问，系统还要结合历史问题和回答决定下一步。最终会话可以输出面试总结。实际使用的数据库、向量库和模型组件需要以代码为准。

**追问：为什么要拆成这些模块？**

**回答：**拆分的主要原因是不同模块的职责不同。文件解析负责把非结构化内容变成可用事实，检索负责提供和当前问题相关的上下文，问题生成负责组织提问，答案评估负责输出评分和纠错，状态管理负责保证多轮流程不会混乱。如果把这些逻辑都放在一个大 Prompt 里，出现问题时很难判断是文本没有解析出来、检索错了、模型没有遵循格式，还是会话状态丢失。模块拆分后，可以针对每一段单独测试和替换。

### 3. 本地简历导入后如何处理？

**回答：**我会先把本地简历转换成可处理的文本，然后清理页眉页脚、空行和不必要的格式信息，再按教育经历、实习、项目、技术栈和奖项等语义组织内容。项目部分还需要保留项目名称、时间、技术栈和职责之间的关系，否则系统可能只检索到一个技术名词，却不知道它属于哪个项目。之后可以为每个片段补充来源和类别信息，供问题生成和回答评估使用。当前支持的文件格式、解析库和异常处理方式还需要从实际代码中确认。

**追问：如果简历解析失败怎么办？**

**回答：**我会把解析失败分成文件不可读取、文本为空、中文乱码和结构抽取失败几类。文件本身不可读取时，应在入口处给出明确提示；文本为空时不能继续生成问题，要让用户重新上传或粘贴内容；结构抽取失败时，可以保留原始文本作为降级输入，同时提示用户检查结果。对于 PDF 中的图片简历，如果没有 OCR 能力，应该明确告诉用户当前版本不支持，而不是生成看起来合理但没有事实依据的问题。

### 4. 这个项目使用了 RAG 吗？

**回答：**如果项目把简历文本或知识库内容切分、向量化，并在生成问题或评价回答前检索相关片段，那么它包含 RAG。RAG 的作用是把用户自己的项目事实和知识内容提供给模型，减少模型脱离简历泛泛提问。流程上是先准备文档片段，再建立向量表示，生成问题或反馈时根据当前面试模式和问题内容检索相关片段，最后把召回内容放进上下文。具体是否使用向量数据库、Embedding 模型和 Top-K 参数，需要根据实际实现说明。

**追问：为什么不能直接把整份简历放进 Prompt？**

**回答：**整份简历直接放进 Prompt 在内容较少时可以工作，但它有三个问题。第一，简历变长后会占用上下文并增加成本；第二，模型不一定稳定地关注当前项目相关内容；第三，问题和反馈无法方便地追溯到具体来源。检索方式可以先按面试模式缩小范围，再把相关项目片段传给模型。它的代价是要处理切分、召回不准和元数据丢失等问题，所以仍然需要对召回结果做检查。

### 5. 这个项目为什么可以称为 Agent？

**回答：**是否能称为 Agent，关键不在项目名称，而在系统是否根据任务状态和执行结果做下一步决策。如果只是固定地调用“生成问题”和“评分”两个 Prompt，更准确的说法是 RAG 加多轮工作流。如果系统能够识别当前是项目面还是八股面，维护当前面试阶段，根据回答质量决定追问、换题或结束，并通过不同工具完成检索、评估和总结，那么它才具备 Agent 编排的特征。我会根据实际代码选择表述，不会只因为项目名称里有 Agent 就把普通问答说成完整 Agent。

**追问：你的 Agent 有哪些工具或动作？**

**回答：**这个问题需要按真实实现回答。可以被抽象为简历内容检索、项目问题生成、基础知识问题生成、回答评估、追问生成和面试总结等动作。关键是这些动作是否由一个路由流程根据当前状态选择，而不是所有动作固定执行。如果目前只有函数调用但没有条件决策，我会说它是工具化工作流；如果存在会话状态和基于回答结果的分支，我再进一步说明 Agent 的路由逻辑。

### 6. 项目面和八股面是如何区分的？

**回答：**我会把两类面试看作不同的任务目标。项目面需要围绕用户的真实经历提问，例如项目背景、个人职责、技术选型、难点和结果，问题来源主要是简历中的项目事实；八股面则围绕 Java、数据库、Redis、网络或其他技术主题检查基础知识，问题来源可以是知识库或预设主题。系统开始时应记录当前模式，后续生成问题和评分标准都参考这个模式，避免项目面突然变成完全无关的随机题。

**追问：如果用户想同时练项目和八股怎么办？**

**回答：**可以把整体面试拆成多个阶段，例如先进行自我介绍和项目面，再进入基础知识面，最后进入用户薄弱点追问。每个阶段有自己的题型和结束条件，会话上下文仍然保留，但评分标准可以切换。切换时需要明确告诉用户当前进入了什么环节，避免用户不知道为什么问题风格发生变化。如果目前没有实现阶段切换，我会把它描述为不同模式的独立练习，而不会声称已经实现完整的混合面试流程。

### 7. 多轮面试状态如何管理？

**回答：**至少要记录面试模式、当前阶段、当前问题、回答历史、评分反馈和下一步动作。如果用户回答后需要追问，系统要知道追问针对的是哪道原问题；如果用户选择换题，也要保留之前的结果，避免上下文串题。状态可以放在会话对象中，短期交互用内存管理，若需要恢复历史则持久化到数据库。具体采用哪种方式要看实际代码。汇报时我会画一张状态图，说明开始、出题、回答、评估、追问、换题和结束之间的转移。

**追问：怎样避免上下文越来越长？**

**回答：**我会把完整历史和当前推理上下文分开。完整历史用于生成最终报告和用户查看，当前请求只保留当前项目、最近几轮问答和必要的评分摘要。较早的内容可以压缩成结构化摘要，例如已经覆盖的知识点、已发现的薄弱点和未完成的追问。这样既保留训练连续性，又避免每次请求都把整场面试原文发送给模型。是否已经实现摘要压缩，需要在项目中核实。

### 8. 如何生成有区分度的问题？

**回答：**问题生成不能只依赖“请生成一道面试题”这种宽泛提示。我会给模型当前面试类型、目标岗位、项目事实、题目难度和已经问过的内容，要求它输出问题、考察点和追问方向。项目面可以从事实出发逐步深入，例如先问做了什么，再问为什么这样设计，最后问异常和边界；八股面可以先问概念，再问使用条件和常见误区。这样可以减少重复问题，也方便后续评分。

**追问：如何避免模型问出简历里没有的内容？**

**回答：**问题生成时需要把简历片段作为事实边界，要求模型优先围绕已出现的项目、技术和职责提问；如果想考察扩展知识，应明确标记为基础知识题，而不是伪装成用户做过的经历。反馈阶段也要区分“简历中没有说明”和“用户没有回答好”，不能把没有写在简历里的技术当作用户已经负责过。必要时可以在结果中保留引用片段，方便用户检查问题来源。

### 9. 答案评分应该怎么设计？

**回答：**评分不能只让模型返回一个总分，因为用户不知道分数依据。我会先确定评分维度，例如技术正确性、回答完整性、和项目事实的匹配度、边界意识以及表达结构，具体维度以实际实现为准；然后要求模型对每个维度给出分数和理由，再输出遗漏点、错误点和改进建议。程序最好要求结构化 JSON，前端按字段展示。这样用户可以看到自己是概念错、项目边界没讲清，还是缺少验证结果，而不是只看到一个不可解释的数字。

**追问：为什么让大模型评分，结果不会很主观吗？**

**回答：**会有主观性，所以评分不能被当成绝对客观的考试成绩。我的做法应该是通过固定评分标准、固定输出格式、提供参考要点和限制回答上下文来降低漂移，并用一组人工标注样例做离线对比。如果同一回答多次运行分数差异很大，就说明评分提示或标准还不稳定。汇报时我会把它称为“辅助评估和反馈”，不会把模型分数包装成经过严格验证的真实准确率。

### 10. 系统如何给出改正建议？

**回答：**改正建议应该先判断回答中哪些内容是正确的，再指出缺失、错误或越界的地方，最后给出一个更完整的回答结构。项目题的改正重点通常是背景、个人动作、技术机制、难点和验证结果；八股题的改正重点通常是概念定义、适用边界、实现原理和常见误区。反馈不能直接替用户编造项目成果，尤其是指标、负责范围和上线效果。如果原简历没有证据，建议应写成“需要补充验证”，而不是替用户填一个数字。

**追问：如何保证改正后的答案仍然符合用户经历？**

**回答：**我会把改正建议建立在简历事实和用户原回答上，要求系统区分已确认事实、用户没有提到的内容以及待补证据。对于技术解释可以补充通用知识，但对于个人职责和结果必须回到简历或用户确认的信息。输出中可以把“可直接复述的版本”和“需要本人确认的补充点”分开，这样用户不会把模型生成的合理推测误当成自己真正做过的事情。

### 11. 模型输出不是合法 JSON 时怎么办？

**回答：**结构化输出失败是大模型应用里常见的问题。我会先在 Prompt 中明确字段、类型和禁止的额外文本；调用后对结果做解析校验，缺字段或类型错误时尝试一次有限修复；仍然失败则保留原始回答并给用户明确提示，不把错误内容直接当成评分展示。对于评分结果，宁可降级成普通文本反馈，也不能把缺失的分数当作零分。具体重试次数和降级策略需要以代码为准。

**追问：重试会不会造成成本和延迟问题？**

**回答：**会，所以重试必须有上限，并且只针对可恢复的格式错误，不应该对所有业务错误无限重试。可以把解析失败、模型超时和内容不安全分开处理：解析失败进行一次格式修复，超时走明确的失败提示，内容安全问题直接停止。后续可以记录每类失败次数和平均耗时，判断是否需要换模型或改输出协议。当前如果还没有这些观测数据，我会把它们列为待测，而不是声称系统已经达到某个稳定性指标。

### 12. 简历隐私如何处理？

**回答：**简历包含姓名、联系方式、教育经历和项目细节，隐私边界需要在设计时明确。首先要知道文件是否只在本地处理，还是会把文本发送给外部模型；如果调用外部服务，应在用户侧提示并尽量脱敏。日志中不应直接记录完整简历、手机号和邮箱，错误日志只保留必要的会话标识。若项目使用本地模型，可以强调原始文件不需要离开本机，但仍要检查模型服务和数据库的存储位置。具体部署方式目前待补充。

**追问：为了提升效果，你会不会把全部简历内容都发送给模型？**

**回答：**不会默认这么做。完整简历可能包含与当前问题无关的个人信息，也会增加上下文长度。我会先按照当前面试类型检索项目或知识片段，只发送完成当前任务所需的内容；联系方式等信息不应该进入问题生成和评分上下文。如果某次任务确实需要整份简历，也应该先进行字段筛选和脱敏，并在日志里避免保存原文。

### 13. 文字面试和真实面试有什么差别？

**回答：**文字面试能覆盖问题生成、回答分析、知识纠错和流程编排，但不能评价语速、语气、停顿、表情和即时沟通压力。因此我会把当前系统定位成文本式 AI 面试陪练，而不是完整替代真实面试。它更适合帮助用户整理项目表达、发现知识缺口和反复练习。未来可以接入语音识别和语音合成，但这属于新增的输入输出链路，不能因为已经支持文字交互就声称完成了语音面试。

**追问：为什么先做文字版本？**

**回答：**文字版本可以先验证最核心的产品闭环：简历事实是否被正确使用，问题是否有相关性，评分和纠错是否有帮助，以及完整会话是否能顺利结束。语音功能会引入识别错误、音频流、延迟、设备兼容和隐私等额外复杂度。如果核心评分逻辑还没有稳定，直接增加语音只会扩大问题范围。所以我会先把文本流程和反馈质量验证清楚，再考虑语音扩展。

### 14. 如何验证问题和反馈质量？

**回答：**我会建立一组人工准备的简历片段、项目事实、标准问题和参考要点，分别测试项目面和八股面。问题质量可以看是否相关、是否重复、是否超出事实边界；反馈质量可以看是否识别关键缺失、是否指出真实错误、是否给出可执行的改进方向。评分一致性可以对同一回答重复运行比较结果，但这只能说明稳定性，不能直接证明正确性。最终仍需要人工抽样审核和记录边界样例。

**追问：你现在有准确率或用户满意度数据吗？**

**回答：**目前没有可以直接写入简历的准确率、覆盖率或用户满意度数据，因此我不会编造这些指标。更稳妥的做法是先建立测试集，记录问题相关性、评分差异、格式错误率和流程完成率，明确测量口径后再决定是否写进简历。如果暂时只有个人试用，我会把结果描述为“完成核心流程验证”或“形成可运行原型”，而不是声称达到生产级效果。

### 15. 这个项目目前最大的不足和下一步是什么？

**回答：**目前最大的风险是功能看起来完整，但如果评分标准、状态管理和测试证据不足，容易退化成多个 Prompt 的拼接。下一步我会优先补齐评分 Rubric、会话状态图和离线评测集，验证问题是否贴合简历、评分是否稳定以及异常流程是否可恢复。之后再考虑历史报告、知识库更新、语音交互和多模型切换。这样迭代顺序是先证明核心闭环有效，再扩展交互形态，而不是先堆更多功能。

**追问：如果让你删掉一个功能，你会删掉什么？**

**回答：**如果当前评分逻辑还没有稳定，我会先删掉复杂的“全流程面试”扩展，把范围收敛到简历导入、单题生成、回答评估和复盘建议。因为这四步是最小可验证闭环，能够直接检验项目的核心价值。等单题评分和反馈质量有测试依据后，再增加追问、阶段切换和历史报告。这样可以减少状态分支，先把核心能力做深，也方便面试时清楚说明项目边界。
